## 0.1.6

Buffer reported, for an Instagram post: "Instagram could not publish this post: the image's aspect ratio is not supported. Use an image between 4:5 and 1.91:1." Instagram refuses feed images narrower than 4:5 or wider than 1.91:1, with no rounding. Buffer cannot crop: the plugin sends `assets: [{ image: { url, metadata: { altText } } }]`, all `ImageAssetInput` takes (developers.buffer.com /reference.md), and Buffer's support documentation says to crop before posting. Separately, a test site filled with sample data showed five admin problems: React logged "two children with the same key" for `buffer:range`, the engagement and impressions charts gave four channel lines no way to tell them apart (and, once named, the four "(Not split)" lines read "Facebook in pink, Instagram in orange, Threads in pink, LinkedIn in orange"), Send again sat beside a post still queued in Buffer, the Channels table showed "3%" beside "4.2%", and the Setup view wrote "2026-10-09" beside "9 Oct 2026, 6:55 am AEDT".

- Instagram's image shape (`src/publish/aspect.ts`, new, pure). `fitsInstagram` is integer maths, `5 * w >= 4 * h` and `100 * w <= 191 * h`, so both edges are in (800x1000, 1910x1000) and 1024x536 (1.9104:1) is out. `shapeProblem` answers only for the `instagram` service and only when the width and height are whole numbers above zero.
- The image's size comes from the image field's own value, `width` and `height` (emdash 1.1 src/media/types.ts `MediaValue`), else the same under `meta` (`sizeOf` in `src/publish/image.ts`). No bridge call: the value is in the entry. The SEO image, a bare string and a value without a size have no known size, and when the SEO image stands in for a local image without an address, the field's size is not used for it.
- Publishing (`prepareDeliveries`): an Instagram channel whose image is known to be outside the range gets a `skipped` record with the new reason `imageAspect`, after the text is fitted, so the record keeps the text, link and image, plus `imageWidth` and `imageHeight`. Nothing goes to Buffer for it. An image of unknown size is sent as before. Every other network is unchanged. Stored records are not touched.
- Send again (`src/ui/panel.ts`) is offered for an `imageAspect` record as well, and for any Instagram record it works the image out again from the published entry first (`repairImage`, one `content.get`, the same path 0.1.4 added for image addresses that need signing in). `repairImage` now skips an Instagram record whose image is still the wrong shape as `imageAspect`, so the post goes out only once a differently shaped image is published. An edit saved as a draft is not seen until it is published.
- Messages: the panel and the delivery say "The image is 3:1. Instagram accepts 4:5 (tall) to 1.91:1 (wide). Choose a differently shaped image, publish the change, then use Send again." The shape is "3:1", "3:10" for small whole ratios, else a decimal against 1 with enough places never to read as an edge it is past ("1.9104:1"). `reasonText` has a sentence without the shape for a record that lacks the size.
- Editor panel warning before the first share: for each Instagram channel the entry would go to (on, not blocked, not left out), "My Instagram (instagram) will skip this entry: its image is 3:1. Instagram accepts 4:5 (tall) to 1.91:1 (wide)." as an alert banner. It is worked out from the entry the panel already reads, so a load costs the same bridge calls.
- `imageAspect` is in `SKIP_REASONS`. `channel_health`'s `blocked.reason` enum now comes from `BLOCKED_REASONS`, which is `SKIP_REASONS` without `imageAspect`: a channel is blocked only by `channelBlocker`, which never gives that reason, and the enum stays the one 0.1.5 declared. The delivery `reason` in `entry_status` and `recent_deliveries` was already a free string. The built manifest's `mcp` section is byte for byte the 0.1.5 one.
- Send again is offered only for a post Buffer is done with: `postStatus` `sent`, `error` or `notFound` (`canSendAgain`). Never for `scheduled`, `sending`, `draft`, `needs_approval` or a status not read yet, where a second post would sit beside the first. Both presses check it. A failed delivery keeps Retry.
- Range buttons: each has its own `action_id`, `buffer:range:7`, `buffer:range:30` and `buffer:range:90` (`rangeAction`), and the handler reads the days from the id (`rangeOf`). The admin keys an actions block's buttons by `action_id`, which caused the React warning. The bare `buffer:range` with the days in the value, which a page drawn by 0.1.5 sends, still works. The panel, the widget and the other button rows already had distinct ids.
- Chart lines: EmDash registers no ECharts legend component (@emdash-cms/blocks 1.1.0 and 1.2.0 `echarts.use`: bar, line, pie, aria, axis pointer, grid, tooltip), although its sanitiser would keep a `legend` key, so a legend would draw nothing. Under each figure chart a context line names each line, its colour and its line ("Lines: Facebook (Direct) in solid blue, Facebook (Buffer) in dashed blue, Threads (Not split) in dotted pink."), from `SERIES_COLOUR_NAMES` beside `SERIES_COLOURS`.
- Chart line looks (`seriesLook`, replacing 0.1.4's `seriesColour`). 0.1.4 gave each channel three palette places, Direct, Buffer and Not split, whether or not each had a line, and cycled kumo's six colours over them. Three places against six colours meant every channel's Not split fell on place 3k + 2, which is pink or orange, so four unsplit channels drew two colours twice; Direct and Buffer did the same when only one origin had lines. Now the channel picks the colour, by its place among the shared channels in Buffer's order, and the origin picks the line: Direct solid, Buffer dashed, Not split dotted, sent as `lineStyle.type`, which EmDash's custom chart sanitiser keeps (@emdash-cms/blocks 1.1.0 `sanitizeOptions` strips only `formatter`, `rich`, `graphic` and `axisPointer`). A channel's lines share one colour, a channel and origin look the same on both charts and every range, and up to ten channels need no more than colour and line. Colour by channel was chosen over a colour per channel and origin because six or ten colours run out three times as fast that way, and a reader matches a channel's lines by colour.
- Colours past the host's six (`EXTRA_COLOURS`): green #3A9C3E, red #C8323C, olive #8A9A1B and grey #7D8590, picked away from the palette's hues. Past ten channels the colours come round again with a point marker (squares, triangles, diamonds, pins, arrows, drawn at 7 px so the shape shows), sixty channels before a look repeats. `distinctLooks` settles a repeat on one chart (a channel missing from the shared list, or more than sixty channels) by moving the later line to the next free look, so no two lines on a chart look or read alike.
- Colour names: kumo calls #F5B647 Yellow, but its hue is 38 degrees, nearer the palette's orange #D37536 (24) than yellow (60), so the page now calls it amber.
- `formatRate` always shows one decimal place ("3.0%").
- Setup view: the watch start and the channel read are shown with `formatTime` ("9 Oct 2026, 6:55 am AEDT"), and the origins line's day with `formatDay`, in the Time zone setting, instead of a bare day key.
- Wording: "Buffer's channel configuration, read {time}, added nothing to the documented rules, so every rule here is Buffer's documented default." replaces "refined no rule".
- Tests: `tests/aspect.test.ts` (both edges, one pixel past each, 1024x536 and 1023x536, 3000x600, 600x2000, `formatRatio`, `sizeOf`); `tests/services.test.ts` (the `imageAspect` skip keeping the post, the size from `meta`, unknown sizes sent, only Instagram affected, a configuration hint of no image); `tests/panel.test.ts` (the warning and its absence, a publish that skips Instagram without asking Buffer, Send again refused while the image is unchanged and sent once a new one is published, Send again hidden for every open post status); `tests/budget.test.ts` (a publish with Instagram skipped, and an Instagram Send again that reads the entry and is rate-limited, both within ten calls); `tests/analytics.test.ts` (distinct range ids and the old id, the line names, no `legend`, rates; four channels all Not split drawing four colours, dotted, with four different descriptions; four channels split into Direct and Buffer, one colour per channel and solid against dashed; a channel's look kept across both charts and ranges; 25 channels past six colours with no look or description repeated; 70 lines and channels missing from the list settled by `distinctLooks`; ten channels over 90 days with unique descriptions); `tests/page.test.ts` (the Setup view's dates).
- No permission, capability, setting or MCP tool changed, and no tool output changed, so the update asks for no approval and Agent access stays on. The registry changelog and FAQ tabs changed, so the package profile needs `emdash-plugin update-package`.

## 0.1.5

On fueloracle.com.au (0.1.4), checked against publish.buffer.com/insights on 9 October 2026: Buffer showed a Facebook post published "Sep 27, 8:15 AM" Sydney time (2026-09-26T22:15Z), and the plugin's Engagement by day and Impressions by day charts put its 1 interaction and 114 impressions on 26 September. Every other figure matched Buffer (engagement as reactions, comments and shares, the engagement rates, impressions a day behind as Buffer refreshes them). Every day key was a UTC day: `utcDay()` in `src/store/report.ts` (`toISOString().slice(0, 10)`) and the windows built from it in `src/sync/aggregates.ts`, `src/sync/metrics.ts` and `src/report/figures.ts`, and `src/ui/format.ts` formatted with `timeZone: "UTC"`. So a post made before 10 am (11 am in daylight saving) in Sydney landed a day early, and "Last N days", "today is still counting" and the daily sync turned over at UTC midnight.

- New setting `timeZone`, "Time zone" (string, default `Australia/Sydney`), in the manifest and `src/settings.ts`. EmDash gives a sandboxed plugin no site time zone: `SiteInfo` (`ctx.site`) is name, url, locale and trailingSlash in emdash 1.1.0 and 1.2.0 (`createSiteInfo` in dist/context-*.mjs), the site's own `site:timezone` setting is not exposed, and `routeCtx.ui` carries only the locale. The name is checked with `Intl.DateTimeFormat` and its canonical spelling kept ("australia/sydney" becomes "Australia/Sydney"), and anything the runtime does not know falls back to `Australia/Sydney`.
- `src/time/zone.ts` (new, no imports): `dayOf` (the day a moment falls on, from `Intl.DateTimeFormat` parts), `dayStart` and `dayEnd` (the first and last second of a day in the zone as UTC instants, worked out from the zone's offset at the guess and at the result, so a day on which the clocks change is 23 or 25 hours and a zone whose clocks skip midnight starts at its first real second), and `addDays` and `daysBetween`, which are calendar arithmetic on `YYYY-MM-DD` and do not depend on the zone. No offset is written by hand. `src/store/report.ts` re-exports `addDays`, `daysBetween` and `Day`, and `utcDay` is gone.
- Buffer queries. `aggregatedPostMetrics` (`src/sync/aggregates.ts`): a day's window is `dayStart` to `dayEnd` (27 September in Sydney is `2026-09-26T14:00:00Z` to `2026-09-27T13:59:59Z`, 4 October `2026-10-03T14:00:00Z` to `2026-10-04T12:59:59Z`), and a 7, 30 or 90-day range runs from the first day's start to today's end. The posts read (`src/sync/metrics.ts`) asks for `createdAt` from the start of its first day in the zone, and each post goes to the day its `sentAt` (else `dueAt`, else `createdAt`) falls on in the zone. The status pass and the unknown-delivery look-up already used real instants and are unchanged.
- Days in the zone everywhere else: "today" and the done-for-today checks of the metrics and aggregates phases, the origins phase's pruning, `periodOf`, `sentDay`, the failed day, `sendsByDay`, `ledgerReaches`, `channelTotals` and `topEntries` (`src/report/figures.ts`), the day the last origins pass covered to (`src/ui/analytics.ts`), the Setup view's dates (`src/ui/page.ts`) and `engagement_summary`'s window (`src/tools/load.ts`).
- Labels (`src/ui/format.ts`): `formatTime` shows a moment in the zone with its short name ("27 Sept 2026, 8:15 am AEST") instead of UTC. `formatDay` shows a moment as its day in the zone and a calendar day as the date it names, and `formatShortDay` (chart labels) shows the day key as it is.
- On update. The `aggregates` and `origins` rows now carry `zone`, and the report state `dayZone`. A row without a zone (written by 0.1.4 and earlier, keyed by UTC day) or with another zone reads as empty, so the pages and `engagement_summary` show no daily figures from it. The first sync after the update sees no `dayZone` and drops the state's days (`settleDayZone`): `metrics`, `aggregates`, `origins` and a pass under way go, and `insightsHistory` is kept. The metrics pass and the aggregates phase are then due at once, the aggregates phase starts from an empty row, reads the last 30 days and the ranges again and backfills older days as before (`catchup-a` and `catchup-b` while work waits), and the origins phase replaces the `origins` row when the pass is done. A day older than Buffer's history limit cannot be read again, so on the Free plan (31 days) the figures by day start 31 days back. A plan without a limit fills 180 days again. The ledger keeps real timestamps and is placed by day each time a page is drawn, so it needs no rebuild. The rebuild costs no bridge call of its own (the rows are read and written by the phases anyway, the state is written at the end of every run), and its Buffer requests are the same ones a new install makes. Changing the setting later rebuilds the same way.
- The Analytics page, the widget and the editor panel read the setting they already read. `engagement_summary` now reads settings too: 3 bridge calls instead of 2.
- Tests: `tests/zone.test.ts` (the 26 September post on 27 September in Sydney, inside that day's window and outside the 26th's; the posts read's start; 4 October 2026 at 23 hours and 5 April 2026 at 25 hours; windows over 28 September to 8 October meeting second to second; Santiago's skipped midnight; the setting's fallback; labels in the zone). `tests/sync.test.ts` runs a 0.1.4 state and UTC row through a sync. `tests/budget.test.ts` counts that sync. Tests that assumed UTC now build days in `Australia/Sydney`.
- The registry listing has a banner, `images/banner.webp`, declared as `release.artifacts.banner`. It is 1536x512 WebP (33 KB), the 3:1 shape the registry shows, so link previews show it whole.
- No permission or capability changed. A settings field asks for no approval (on update EmDash compares added capabilities, newly public routes and the manifest's `mcp.tools`, not `settingsSchema`: emdash 1.1.0 dist/api-*.mjs). The MCP tool descriptions now say `engagement_summary`'s days are in the Time zone setting, not UTC (`src/tools/declare.ts`: the day field, `until` and the `days` window). That changes `mcp.tools`, so EmDash turns Agent access off after the update. Turn it on again under Plugins. On fueloracle.com.au (0.1.3) the first Share now, the Gunbarrel post to Facebook, Instagram and Threads, failed on all three: Buffer said "Invalid post: Image could not be read from its URL." With no public address, or when the entry cannot be read, the record goes without the image and says why in `imageIssue` (`noPublicAddress`, `entryUnreadable`), and a network that needs an image is skipped with `needsImage`. A run sends one repaired record beside its reserve and continues with the rest.
- `media:read` is no longer used, and is kept in the manifest for this release so the update asks for no approval.
- Charts: a line with no value on any day drawn is left out of every chart (`dailyChart`), so it takes no colour and no tooltip row. A line with zeros on covered days but no reported figure stays out, as in 0.1.3.
- Charts: each channel and origin keeps one colour on both figure charts and on every range. The shared channels in Buffer's order, each with Direct, Buffer and Not split, take the host palette in turn (`seriesColour`), counting every channel and origin whether or not it has a line, so leaving a line out moves no other line's colour. Kumo's dark palette differs only in its yellow (#EEB720), which a set colour does not follow. The gradient under a single line is in that line's colour. The sent and failed chart keeps the host's default colours.

- Insights history limit (`src/buffer/history.ts`): learnt from Buffer's message (`limited to the last N days`, `N days of history`, case-insensitive), never written down per plan, and kept as `report.insightsHistory` (`days`, `learntAt`, `checkedAt`) in the report state every run writes anyway. A refusal of a request already cut to N takes the limit one day shorter (Buffer may count days in the organisation's time zone). Used by `aggregatedPostMetrics` (typed `AggregatedPostMetrics!`, so GraphQL's own rules null the whole answer on one refusal; the partial case is handled in case Buffer answers otherwise). The aggregates phase keeps the answered aliases, learns from history refusals among the rest, and shows any other error.

## 0.1.1

Buffer's rate limits are per account, not per key: "MCP connections share one rate-limit bucket with your personal API keys", every request counts whether it succeeds or fails, and only a 429 is refunded (developers.buffer.com /guides/api-limits.md, /guides/efficient-api-usage.md). This release makes the plugin a considerate user of that shared bucket.

- A shared-bucket guard (`src/buffer/headroom.ts`, pure): the newest reading of each RateLimit window, matched by `w` and good until `t` seconds after it was taken, from the delivery state, the channel snapshot and the report state. Background reads (channel refresh with configuration, status, metrics, aggregates) check it before every request and stop while the 15-minute window has fewer than max(20, 20% of quota) left or the 24-hour or 30-day window has less than the new `headroomPercent` share. The pause is recorded as `report.headroom` (not `report.problem`), starts no catch-up chain, and lifts when the window resets. The aggregates backfill additionally runs only while the 24-hour window is at least half full.
- Publishing (the hooks, continuations, unknown look-ups, Retry, Send again, Share now) uses only the publish check: it holds while a window has `r` = 0 and waits for that window's reset, as after a 429. A continuation that waits for Buffer is scheduled for the reset, not a minute later.
- Every Buffer answer's RateLimit reading is kept: report runs carry it in the report state they already write (no extra bridge call).
- New setting `headroomPercent`, "Leave for other tools" (number, 25, 10 to 75), in the manifest and `src/settings.ts`. Settings fields need no re-approval.
- The recurring sync is staggered: each install picks a random minute offset once (`state.syncOffset`), and the cron expression is built from the interval and the offset (for example `8,38 * * * *`), never on :00 or :30. Existing installs move on their next activation or page load.
- The Analytics and Setup views show "Reports paused to leave Buffer requests for your other tools until ...". The Setup view's requests-left line uses the newest reading the plugin holds.
- Editor panel Share now: an entry first published before `watchSince`, with no records, offers administrators the per-channel choices and a confirmed Share now that runs the normal pipeline for that one entry (`shareNow` in `src/publish/pipeline.ts`), with `origin: "manual"` on its records ("Shared by hand"). It refuses an entry that is not published, one published after the watch, and a second press. `watchSince` is never changed. Editors see a line and the link to the Buffer page.
- UI: the dashboard card has three stats (sent, failed, queued) and engagement as a context line; a stat card without figures says "None yet"; a range with nothing sent shows an empty block instead of a 0 to 1 chart; the Setup view marks each rule "(documented)" or "(from Buffer)" and says when the configuration was read. Panel times stay UTC: EmDash 1.1 gives plugins no site time zone (`SiteInfo` and `routeCtx.ui` carry only the locale).
- The manifest description now names the dashboard, editor panel and MCP tools (132 graphemes, tested against the registry's 140 cap), and the README and registry description open the same way.
- Docs: a README section "Buffer's API limits" with the limits per plan, what happens when they are reached (posts wait and go out by themselves when the window refills, reports pause first, Buffer's separate per-channel posting limit needs Retry) and what to do if it keeps happening. The registry FAQ and Installation tabs say the same in short.
- `channel_health` reports the newest RateLimit reading of the three stored. Its output schema is unchanged, so Agent access stays on after the update. No permission or capability changed.

## 0.1.0

First release. Shares newly published EmDash entries to Buffer through Buffer's GraphQL API with a personal API key, and reports how each post did:

- sharing on publish (and on create-as-published) for the collections you choose, to every network Buffer's API can post to, following one rule table built from developers.buffer.com, with Buffer's Experimental per-channel configuration read daily as a hint only
- text fitted to each network's limit as Buffer counts it, shortening only the excerpt; the entry's image (public `https` on the site's host or a media provider's address) or a link card where Buffer documents one, never both; optional UTM tags
- tracked delivery per entry and channel: waiting, sending, sent (followed to the live post), unknown (looked up in Buffer before any resend), failed (Buffer's message, retried only on request) and skipped (with the reason); 429s wait out Retry-After
- a Buffer page: analytics over 7, 30 or 90 days (sent, queued, failed, impressions, engagement, top entries, per channel, banners) and a Setup view (channels, collections and image sources, link tags, failed deliveries)
- a dashboard card for the last seven days
- an editor panel on saved entries: per-channel skip and custom text before the first send, each channel's state after, Retry and a confirmed Send again for administrators
- four read-only MCP tools: `entry_status`, `recent_deliveries`, `channel_health`, `engagement_summary`
- registry page sections (description, installation, FAQ, changelog, security)

Every invocation stays within EmDash's ten bridge calls; `tests/budget.test.ts` counts each one.
