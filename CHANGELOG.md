## 0.1.4

On fueloracle.com.au (0.1.3) the first Share now, the Gunbarrel post to Facebook, Instagram and Threads, failed on all three: Buffer said "Invalid post: Image could not be read from its URL." Separately, the Engagement by day chart held a line "Threads (Not split)" with one value (1 on 13 September), a single 4 px point that was easy to miss, and it took the palette's first colour, so "Facebook (Direct)" was yellow there and blue on Impressions by day, where Threads has no line.

- Images now use the site's public media address. 0.1.3 and earlier sent an address that needs signing in, so Buffer could not read the image. The image came from `ctx.media.get(id).url`, which is `/_emdash/api/media/asset/<id>/<filename>` (emdash 1.1 src/plugins/media.ts). That route asks for `media:read` and answers 401 to anyone not signed in. The public route is `/_emdash/api/media/file/<storageKey>` (src/astro/routes/api/media/file/[...key].ts). `src/publish/image.ts` now follows EmDash's own order for a local image value: a `src` under the public file route (or an absolute https `src` on the site's host) as it is (src/loader.ts normalizeLocalMediaValue), else the route plus `meta.storageKey` (src/components/EmDashMedia.astro, src/media/local-runtime.ts getEmbed), each key segment percent-encoded. The media id is never used as a key: it is not the storage key. A local value with neither falls back to the SEO image, keeping the field's alt text, else there is no image, so a network that needs one is skipped (`needsImage`) and the others send a link card or text by their rule. The SEO image resolves as EmDash's `buildSeoImageUrl` does: absolute as it is, a site path joined to the site's URL, a bare reference under the public file route. Image resolution makes no bridge call, so a publish, Share now and the content hooks each spend one call less.
- `publicImageUrl` refuses any path under `/_emdash/api/media/asset/`, case-insensitive and after percent-decoding and dot-segment removal.
- Records stored by 0.1.3 with an image under `/_emdash/api/media/asset/` are repaired before they are sent: a delivery run (after Retry, Retry all, or for a record still waiting) and Send again read the entry (`ctx.content.get`, one bridge call per entry per invocation, counted in `tests/budget.test.ts`) and work the image out again by the rules above. With no public address, or when the entry cannot be read, the record goes without the image and says why in `imageIssue` (`noPublicAddress`, `entryUnreadable`), and a network that needs an image is skipped with `needsImage`. A run sends one repaired record beside its reserve and continues with the rest.
- `media:read` is no longer used, and is kept in the manifest for this release so the update asks for no approval.
- Charts: a line with no value on any day drawn is left out of every chart (`dailyChart`), so it takes no colour and no tooltip row. A line with zeros on covered days but no reported figure stays out, as in 0.1.3.
- Charts: each channel and origin keeps one colour on both figure charts and on every range. The shared channels in Buffer's order, each with Direct, Buffer and Not split, take the host palette in turn (`seriesColour`), counting every channel and origin whether or not it has a line, so leaving a line out moves no other line's colour. The palette is kumo's light categorical palette (@cloudflare/kumo 2.6.0 ChartPalette.categorical: #4290F0, #F5B647, #E8649D, #8D58EE, #50C3B6, #D37536), set per series as `itemStyle.color` and `lineStyle.color`, which EmDash's custom chart sanitiser keeps (it strips only `formatter`, `rich`, `graphic` and `axisPointer`). Kumo's dark palette differs only in its yellow (#EEB720), which a set colour does not follow. The gradient under a single line is in that line's colour. The sent and failed chart keeps the host's default colours.
- No permission, capability or MCP tool changed, and no tool output changed, so Agent access stays on after the update. The registry changelog tab changed, so the package profile needs `emdash-plugin update-package`.

## 0.1.3

On fueloracle.com.au (0.1.2) Engagement by day and Impressions by day each showed one line, "Facebook (Direct)", with points only on the days that had posts (12, 13, 23, 25 and 26 September). The line was drawn straight between them, so five interactions on five days read as a constant 1 from the 12th to the 26th, the axis ran from the first point to the last instead of over the range, and the tooltip said "23 Sept, 10:00:00" for a UTC day seen from Sydney. The confirmation dialog of Share now had its title, text and buttons flush against its edges.

- Charts by day are `chart_type: "custom"` with a category x-axis of day labels ("23 Sept", `formatShortDay`), built by `dailyChart` in `src/ui/blocks.ts`, which replaces `timeseries`. EmDash 1.1 draws a timeseries chart with kumo's TimeseriesChart, whose tooltip formats the x value with a fixed Intl.DateTimeFormat (month, day, hour, minute, second) in the viewer's zone, so no timestamp gives a date alone, and its series take only [number, number] points, so a day without a value can be neither a gap nor on the axis. The custom chart's tooltip is ECharts' own: the day label, a row per line and "-" for a missing day. The host strips every `formatter` key and registers no legend component, so the options are plain data. The rest copies kumo's timeseries options: axis names, dashed split lines, the grid, the default palette, a gradient under a single line and stacked bars.
- Engagement and impressions span every day the figures can cover (7, 30 or 90 days, cut to the learnt history limit). On a day Buffer's post list covers (from `origins.coveredFrom` to the day of the last pass), an origin with no posts is 0. A day not read, a day beyond the history limit, a day with posts whose network reported no figure for the metric, and a day with posts Buffer has not read yet (`unread`, which could be either origin) have no value. A derived channel is 0 on a day Buffer's aggregate counts no post beyond the listed ones. A direct or Buffer line with no post in the range is left out, and a line is left out of a chart when Buffer reported none of that chart's figure, so a network without impressions draws no line of zeros. The split totals on the stat cards add only reported figures.
- Sent and failed by day spans the whole range too, with no bar (and "-" in the tooltip) for days before the plugin started watching.
- A Block Kit response is capped at 2,000 JSON nodes. Each figure chart holds at most 500 values, so with many channels over 90 days a chart keeps its busiest lines and the page says "Each chart shows its 4 busiest lines of 20. A shorter range shows more." Ten channels split two ways over 90 days come to about 1,700 nodes.
- Editor panel: Share now and Send again ask in the panel instead of the host's button `confirm` dialog, which EmDash 1.1 draws in kumo's Dialog with no padding and a plugin cannot style (emdash-cms/emdash#3644, open). The first press re-renders the panel as a banner ("Share this entry to 3 channels now?" or "Send this entry to FuelOracle (facebook) again?"), the channels by name, "It goes to Buffer as if it had just been published. Only this entry is shared." and two buttons, the action (primary) and Cancel. Only the second press acts. The step is in the action id (`buffer:panel:share:confirm`, `buffer:panel:again:confirm`, `buffer:panel:cancel`) and Send again's record id in the value. Both presses check `plugins:manage`, an earlier share or a send under way, the entry published and first published before the watch, a key, the master switch and a channel left in. The first press costs 5 bridge calls for Share now and 3 for Send again, and the confirmed press is unchanged.
- Setup view: "Entries first published after the plugin started watching are shared automatically. Share an older entry with Share now in its editor panel."
- No permission, capability or MCP tool changed, and no tool output changed, so Agent access stays on after the update.

## 0.1.2

On fueloracle.com.au (Free Buffer plan, 0.1.1) the Analytics page showed "Buffer did not answer the last check: Free-plan Insights are limited to the last 31 days of history." The daily windows of the last 30 days worked, but the 7, 30 and 90-day range batch and the 180-day backfill asked for older days and Buffer refused the whole request, so the Channels table had no figures. Buffer does not document a per-plan history limit (the reference's OrganizationLimits has no such field, and the guides do not mention one); it appears only in that error message.

- Insights history limit (`src/buffer/history.ts`): learnt from Buffer's message (`limited to the last N days`, `N days of history`, case-insensitive), never written down per plan, and kept as `report.insightsHistory` (`days`, `learntAt`, `checkedAt`) in the report state every run writes anyway. From then on the aggregates backfill stops at today minus (N - 1), a range longer than N covers N days and keeps `days` beside its figures, the daily re-read and the posts window stay inside it. It is not a failure: nothing goes on `report.problem`, `aggregates.failedAt` is not set, and a request refused for the limit alone is asked again at once, cut to it, while the invocation has a call for it and one for the row write beyond the run's reserve, else on the next run. A refusal of a request already cut to N takes the limit one day shorter (Buffer may count days in the organisation's time zone). Once a week one day just beyond N is asked for alone; an answer drops the limit and the ranges are read again in full. A history refusal stored by 0.1.1 as `report.problem` is dropped on the first run and never shown.
- Partial GraphQL answers: error-handling.md documents errors only with `data: null` and says nothing about `path` or partial data. `graphql()` takes the aliases of a request (`partial`); an answer with data for some aliases and errors whose `path[0]` names only others is a success, with the refused aliases in `refused`. An error naming no alias, an unknown alias or `RATE_LIMIT_EXCEEDED` still fails the request. Every failure now carries all of Buffer's messages in `errors`. Used by `aggregatedPostMetrics` (typed `AggregatedPostMetrics!`, so GraphQL's own rules null the whole answer on one refusal; the partial case is handled in case Buffer answers otherwise). The aggregates phase keeps the answered aliases, learns from history refusals among the rest, and shows any other error.
- Analytics page: when a limit is known, a context line by the range buttons ("Your Buffer plan gives figures for the last 31 days."), the impression and engagement cards and charts and the Channels table's figure columns are labelled with the days they cover ("Impressions, last 31 days"), and the Channels note says so. Sent, failed and queued still cover the whole range. The widget's engagement line keeps to the limit too, should it be under a week.
- Figures by origin. The engagement and impressions charts have one line per shared channel and origin: "<Network> (Direct)" for posts with PostVia `network`, "<Network> (Buffer)" for `buffer` and `api` (Buffer itself, this plugin, other API tools), with the channel's name added when two shared channels are on one network. `aggregatedPostMetrics` cannot filter by origin (AggregatedPostMetricsInput takes only channels, dates and tags), so the split comes from the metrics read: its `posts` query now also selects `via`, `channelId` and `createdAt`, and every listed post is summed per channel, per UTC day of `sentAt` and per origin (`src/sync/metrics.ts`). `posts` filters by `createdAt` and `dueAt` but not by sent time, so the window asks from 7 days before the first day counted (fewer under a history limit) and places each post by `sentAt`. Sums ride in the report state across pages; the new origins phase (2 bridge calls, no Buffer request) files a finished pass in a new `origins` row of the `reports` collection, which the page reads in the same `getMany`. Buffer does not document whether `posts` lists `network` posts: a channel whose pass listed none gets its direct figure as the channel aggregate for the day minus the listed posts, when larger and only when every listed post that day has figures, with the note "Direct figures are Buffer's channel total minus the posts it listed." Days no pass covered stay as "<Network> (Not split)". The Setup view shows each channel's method and the posts Buffer listed by PostVia, read from the report state. Stat cards stay channel-wide and add "612 direct, 108 via Buffer" when every figure in the range is split. The Channels table stays channel-wide and says so. The metrics read asks for the same posts as before, so the split costs no Buffer request.
- `{description}` is another name for `{excerpt}` in post templates: the same text and the same fitting, so a template with both shortens both identically. The default template is unchanged. Every hint that lists the tags names it.
- Naming: the admin page label, the dashboard widget title and the editor panel title are "Buffer Plus", as are the Setup view header and the links to the page. Strings that mean Buffer the service still say Buffer.
- No permission, capability or MCP tool changed, and no tool output changed (`engagement_summary` stays channel-wide), so Agent access stays on after the update.

## 0.1.1

Buffer's rate limits are per account, not per key: "MCP connections share one rate-limit bucket with your personal API keys", every request counts whether it succeeds or fails, and only a 429 is refunded (developers.buffer.com /guides/api-limits.md, /guides/efficient-api-usage.md). This release makes the plugin a considerate user of that shared bucket.

- A shared-bucket guard (`src/buffer/headroom.ts`, pure): the newest reading of each RateLimit window, matched by `w` and good until `t` seconds after it was taken, from the delivery state, the channel snapshot and the report state. Background reads (channel refresh with configuration, status, metrics, aggregates) check it before every request and stop while the 15-minute window has fewer than max(20, 20% of quota) left or the 24-hour or 30-day window has less than the new `headroomPercent` share. The pause is recorded as `report.headroom` (not `report.problem`), starts no catch-up chain, and lifts when the window resets. The aggregates backfill additionally runs only while the 24-hour window is at least half full.
- Publishing (the hooks, continuations, unknown look-ups, Retry, Send again, Share now) uses only the publish check: it holds while a window has `r` = 0 and waits for that window's reset, as after a 429. A continuation that waits for Buffer is scheduled for the reset, not a minute later.
- Every Buffer answer's RateLimit reading is kept: report runs carry it in the report state they already write (no extra bridge call).
- New setting `headroomPercent`, "Leave for other tools" (number, 25, 10 to 75), in the manifest and `src/settings.ts`. Settings fields need no re-approval.
- The recurring sync is staggered: each install picks a random minute offset once (`state.syncOffset`), and the cron expression is built from the interval and the offset (for example `8,38 * * * *`), never on :00 or :30. Existing installs move on their next activation or page load.
- The Analytics and Setup views show "Reports paused to leave Buffer requests for your other tools until ...". The Setup view's requests-left line uses the newest reading the plugin holds.
- Editor panel Share now: an entry first published before `watchSince`, with no records, offers administrators the per-channel choices and a confirmed Share now that runs the normal pipeline for that one entry (`shareNow` in `src/publish/pipeline.ts`), with `origin: "manual"` on its records ("Shared by hand"). It refuses an entry that is not published, one published after the watch, and a second press. `watchSince` is never changed. Editors see a line and the link to the Buffer page.
- UI: the dashboard card has three stats (sent, failed, queued) and engagement as a context line; a stat card without figures says "None yet"; a range with nothing sent shows an empty block instead of a 0 to 1 chart; the Setup view marks each rule "(documented)" or "(from Buffer)" and says when the configuration was read. Panel times stay UTC: EmDash 1.1 gives plugins no site time zone (`SiteInfo` and `routeCtx.ui` carry only the locale).
- The manifest description now names the dashboard, editor panel and MCP tools (132 graphemes, tested against the registry's 140 cap), and the README and registry description open the same way.
- Docs: a README section "Buffer's API limits" with the limits per plan, what happens when they are reached (posts wait and go out by themselves when the window refills, reports pause first, Buffer's separate per-channel posting limit needs Retry) and what to do if it keeps happening. The registry FAQ and Installation tabs say the same in short.
- `channel_health` reports the newest RateLimit reading of the three stored. Its output schema is unchanged, so Agent access stays on after the update. No permission or capability changed.

## 0.1.0

First release. Shares newly published EmDash entries to Buffer through Buffer's GraphQL API with a personal API key, and reports how each post did:

- sharing on publish (and on create-as-published) for the collections you choose, to every network Buffer's API can post to, following one rule table built from developers.buffer.com, with Buffer's Experimental per-channel configuration read daily as a hint only
- text fitted to each network's limit as Buffer counts it, shortening only the excerpt; the entry's image (public `https` on the site's host or a media provider's address) or a link card where Buffer documents one, never both; optional UTM tags
- tracked delivery per entry and channel: waiting, sending, sent (followed to the live post), unknown (looked up in Buffer before any resend), failed (Buffer's message, retried only on request) and skipped (with the reason); 429s wait out Retry-After
- a Buffer page: analytics over 7, 30 or 90 days (sent, queued, failed, impressions, engagement, top entries, per channel, banners) and a Setup view (channels, collections and image sources, link tags, failed deliveries)
- a dashboard card for the last seven days
- an editor panel on saved entries: per-channel skip and custom text before the first send, each channel's state after, Retry and a confirmed Send again for administrators
- four read-only MCP tools: `entry_status`, `recent_deliveries`, `channel_health`, `engagement_summary`
- registry page sections (description, installation, FAQ, changelog, security)

Every invocation stays within EmDash's ten bridge calls; `tests/budget.test.ts` counts each one.
